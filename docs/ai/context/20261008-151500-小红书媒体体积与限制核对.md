# 小红书小工具媒体体积与限制核对

## 用户决定

- 保留开场动画。
- 保留标题曲。
- 保留开场视频。

## 当前证据

- `zip-artifact-spec.md` 把总包小于 2 MB 写在“体积”自检项中，原文是“推荐总包 < 2MB；单图 < 500KB”，没有写成上传硬上限，也没有给出 WebView 运行内存上限。
- 规范的资源加载表允许包内 `<video>` / `<audio>`，但支持文件类型表没有列出 `.mp3`、`.mp4`、`.webm`。这是规范内部冲突，不能据此保证上传校验一定接受视频和音频格式。
- 当前游戏运行时素材约 34.8 MB：PNG 约 7.05 MB，MP3 约 15.35 MB，MP4 + WebM 约 12.4 MB。仓库实际全量音频目录约 340 MB，不应整体打包。
- 标题曲为 187.35 秒、48 kHz、双声道、160 kbps、约 3.75 MB。
- ffmpeg 实测重编码：64 kbps、44.1 kHz、单声道约 1.46 MB；32 kbps、32 kHz、单声道约 0.75 MB。32 kbps 会明显牺牲音乐高频和立体声，64 kbps 更适合作为可接受的低码率版本。
- 开场视频目前为 768x432：`s00a` 约 8.2 秒，`s00b` 约 9.7 秒；MP4 + WebM 双格式合计约 12.4 MB。只保留一种格式可以直接减少约一半，重新编码到 640x360、较低码率还可继续降低。

## 结论与后续

`2 MB` 目前只能按推荐目标理解，不能证明超过后必然无法提交；真正的上传上限和格式白名单需要用小红书上传端或官方后台实测确认。即使没有硬拒绝，保留视频、标题曲和全部音频后，带音频版会远超推荐值。

下一步构建应按“保留用户指定内容、只打包运行时引用文件”执行：PNG 做无损调色板压缩，MP3 先提供 64 kbps 单声道版本，并把 MP4/WebM 做成可切换的兼容版本。构建前还要确认容器是否实际接受媒体扩展名；若不接受，不能靠改扩展名绕过校验。

## 2026-10-08 压缩结果

- 已新增 `游戏/tools/build_compressed.py`，生成 `游戏/dist-compressed/`，原始 `游戏/assets/` 未修改。
- 运行时素材文件数 2876 个，约从 33.32 MB 降到 18.50 MB，减少约 44.5%。
- 标题曲为 64 kbps 单声道，约 1.46 MB。
- 运行时 MP3 全部转为单声道 64 kbps；MP4 转为 640 像素宽、H.264、CRF 30；WebM 转为 640 像素宽、VP9、Opus。
- 用 `data.js` 中的资源引用做完整性检查，2851 个引用候选全部在 `dist-compressed/` 找到。
- 当前仍保留 MP4 和 WebM 两套视频，因此压缩包仍明显高于 2 MB；这是遵循“保留开场视频”的决定，后续应按上传端实测结果选择一种视频格式。
